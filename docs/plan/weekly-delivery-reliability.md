# 周报跨重启补触发与缺失意图告警

[改动计划](README.md) · P1 · 相关：[运维](../operations.md)、[报告与渠道](../reports.md)

## 为什么

2026-10-19 排查确认生产没有显式开启周报，运行配置采用默认 `false`，历史周报定时同步、分析任务和投递意图均为零。当天已通过环境配置开启，并在重启后核对周一调度；首次实际定时投递仍待 10:00（UTC+8）验证。此次配置修复不能证明下面的可靠性缺口已经解决。

周报 cron 只保存在 worker 内存中，重启后只计算未来触发时间；跨过周一发送时刻重启，不会恢复已经错过的触发，`misfire_grace_time` 也不能代替跨进程补偿。现有定时补偿仅覆盖晚报，缺失投递意图的到点告警也只覆盖晨报和晚报，因此可能既没有周报意图，也没有对应漏发记录。

## 改什么

- 先定义周报在部署时区内的计划发送时刻、允许补触发窗口和截止后的处理；不能借用晨报、晚报的期限。报告范围继续使用上一完整周，补偿保留原报告范围和意图日期，不按补偿当天误算另一周。
- worker 启动和周期协调时，按用户及报告周期核对周报定时同步、带 `delivery_period=weekly` 的分析任务和投递意图。窗口内确实缺失时补建同一条持久流程，继续经过同步、分析、已保存快照和 outbox；不让补偿入口直接计算或发送。并发协调、服务重启和重复检查必须幂等。
- 区分尚未到点、配置关闭、未配置投递目标、来源未授权、同步未完成、分析失败、缺快照和意图未创建；到截止仍未生成意图时，使用现有数据库告警和查询接口保留原因。周报关闭时不报预期缺失，也不外发；不新增用户尚未选择的第二告警通道。
- 已受理、已送达或投递不确定的意图不得因补偿再次发送；正在执行的任务遵守租约和所有权，失败重试沿用当前确定性拒绝与退避规则。窗口外保留缺失证据，不用手动补发结果改写自动流程状态。

## 复现与验收

- 先用合成用户和可控时钟复现：到点前启动、运行中短暂迟调度、跨发送时刻重启，以及超过补偿期限后启动。覆盖服务时区、周边界、下一周启动、关闭开关和无授权目标，确认范围、意图日期及是否补建符合明确窗口。
- 覆盖多个协调者并发、重复启动、同步失败或无写入、分析失败、无合格快照，以及已有 `pending/running/accepted/delivered/uncertain` 意图；确认每用户每周最多一条意图，不重发已受理或不确定消息，不把未知记录当作已完成或休息。
- 缺失周报意图时，独立告警检查能在 worker 未运行的情况下记录原因，并可通过 `GET /api/delivery-alerts` 和 `GET /api/deliveries` 查询；未到点和已关闭周报不产生漏发告警。
- 运行对应 scheduler、同步、分析队列、outbox 和告警测试及 `tools/check.py backend`。上线后必须观察一次真实自动定时或受控跨重启补偿链路，逐段核对同步、周报分析任务、正确范围的快照、唯一投递意图和供应商受理标识；未到发送时刻的验收保持待验证。手动补发、直接调用推送方法或仅有周报快照均不能代替自动投递验收，`accepted` 不等于最终送达。

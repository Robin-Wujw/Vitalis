# 缩短同步写事务，避免心跳争用

[改动计划](README.md) · P1 · 相关：[运维](../operations.md)、[数据合同](../data-contracts.md)

## 为什么

2026-10-14 晚报同步和 2026-10-15 晨报同步期间，worker 日志合计出现 6 次心跳写库 `database is locked`，每段同步结束后心跳恢复。两次同步及分析均成功；本次漏发的直接原因是反馈链接触发 `render_failed`，与这里记录的锁争用分开处理。

网络请求已经在数据库事务外执行，不能把上述现象归因为网络持锁。当前普通流的持久化入口先写原始日志，再在同一事务中解析、写标准化事实和更新每日特征；部分大响应可能长时间占用 SQLite 写锁。WAL 允许读写并行，但写者仍然串行，当前忙等待为 30 秒。尚无逐事务耗时证据，不能确定是哪条数据流或哪个阶段造成这 6 次失败。

## 改什么

- 先记录合成复现和生产同步中各阶段的耗时，区分原始日志准备、解析、标准化写入、每日特征聚合以及实际写事务持续时间；只记录流、阶段、耗时与数量，不记录健康原文、凭据或个人标识。
- 把响应序列化、加密准备和可独立完成的解析放到持有写锁之前；依据测量结果处理大批样本写入和每日特征聚合，不能只延长忙等待或放宽心跳阈值掩盖争用。
- 保留来源账户的 epoch、attempt/chunk lease 和完成条件检查，在提交前重新确认当前所有权；过期或撤销的执行不能发布事实或后续任务。
- 同一有效输入的原始日志、标准化事实、每日特征、输入 revision 和受影响分析任务仍须按当前[数据合同](../data-contracts.md)原子提交。任何缩短事务或分批方案都要先定义可见边界，不能留下半提交事实、丢失分析任务或把未完成覆盖标为完整。

## 复现与验收

- 先在 `tests/test_zepp_sync_coordinator.py`、`tests/test_sync_manager.py` 和 `tests/integration/test_worker_heartbeat.py` 添加失败测试：使用磁盘 SQLite、WAL 和两个独立连接，在同步端用慢合成解析器及大批合成样本重现心跳争用；内存单连接测试不能代替此项。
- 测试分别覆盖慢解析和大批写入，确认解析耗时不占用写锁，心跳在同步期间持续完成短事务，延迟有明确上界且小于当前 30 秒忙等待；记录修改前后的最大写事务耗时和心跳间隔。
- 覆盖解析失败、提交失败、账户撤销、lease 过期及重试，确认回滚后没有半提交的原始日志、事实、特征或任务；正常重试幂等，旧执行无法提交。
- 运行对应目标测试和 `tools/check.py backend`；上线后观察至少一个晨报及晚报完整同步，确认心跳连续更新、没有新增 `database is locked`，同步、分析及投递正常，并用阶段耗时解释改善来自哪里。

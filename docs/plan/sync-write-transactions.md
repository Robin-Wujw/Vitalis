# 同步时别让数据库阻塞心跳

[改动计划](README.md) · P1 · 状态：先定位耗时，再改代码

## 现在是什么情况

**同步大量数据时，后台服务可能忙着写数据库，连“我还活着”的心跳都写不进去。**

历史排查记录中，2026-10-14 晚报同步和 10-15 晨报同步期间合计出现 6 次 `database is locked`，同步结束后心跳恢复。两次同步和分析都成功；当时报告漏发的直接原因是另一处排版失败，不能混为一谈。

网络请求已经放在数据库事务外。值得测量的是：现有普通数据流会在一次写入中保存原始响应、解析数据、保存标准化记录并汇总每日特征。SQLite 同一时刻只能有一个写入者，这一段太长就可能挡住心跳。但目前没有逐段耗时证据，不能先断言是哪一步造成的。

2026-11-10 通过 API 补拉 60 天时，实际调度记录显示每 16 个分块间插入的分析分别耗时约 80.5、95.7、112.3 秒；当时未出现失败分块。这只能证明分析调度也影响总完成时间，不能证明它持续占用写锁。测量应分别记录网络、写事务、日级特征汇总和分析耗时。手动同步的 `streams` 可避免无关流的重复取数，但不代替本条目的锁等待与心跳验收。

2026-11-11 MCP API 验收期间，定向睡眠/活动刷新与训练明细同时执行，worker 再出现 SQLite 锁错误，原始 GET 的任务提交出现 `OperationalError`。接口将明确的 SQLite BUSY/LOCKED 错误码作为可重试 503；这只是准确表达临时争用，不是缩短事务或修复心跳阻塞。本条目继续保留，验收写入需等待正在执行的同步完成后使用原幂等键回读或重试。

## 接下来做什么

1. **先测量**：用合成大响应复现，并记录原始响应准备、解析、事实写入、每日汇总各耗时多久，尤其是实际占用写锁的时间。
2. **再缩短占锁时间**：尽量在写库前完成序列化、加密准备和独立解析；大批写入、每日汇总怎样调整，由测量结果决定。
3. **保持同一输入的结果一致**：一个有效同步分片的原始响应、事实、特征、版本号和后续分析任务，要么一起保存，要么一起撤回；不是要求整次多分片同步全成全败。若进一步分批，先明确读者何时能看到结果，不能出现“数据只写一半却标为完整”。
4. **防止旧任务提交**：账号已撤销、任务已过期或执行权已转移时，原执行者不能继续发布结果。

## 怎样算完成

- 在磁盘 SQLite、WAL 模式和两个独立连接上，分别复现慢解析和大批写入的影响；内存单连接测试不算。
- 修改后慢解析不占用写锁，同步期间心跳能持续写入；给出最大写事务耗时和心跳间隔的前后对比，心跳等待上界小于当前 30 秒忙等待时间。
- 解析失败、提交失败、账号撤销、执行资格过期及重试都不会留下半份记录或漏掉分析任务；重复执行不重复写入。
- 目标测试及 `uv run --locked --extra dev python tools/check.py backend` 通过。
- 上线后观察至少一次完整晨报同步和晚报同步：无新增锁错误，心跳、分析和投递正常，耗时记录能解释改善来自哪里。

## 开发时注意

- `epoch` 是来源授权的代次；`lease` 是任务执行权的有效期。提交前必须重新检查，不能因把解析移出事务而放松这些限制。
- 不靠延长忙等待或放宽心跳阈值掩盖问题；WAL 能让读写并行，不能让多个写入同时进行。
- 耗时日志只记录数据流、阶段、数量和用时，不记录健康原文、凭据或个人标识。提交规则见[数据合同](../data-contracts.md)，排障见[运维](../operations.md)。

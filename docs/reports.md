# 报告与渠道

[文档中心](README.md) | [改动计划](plan/README.md) | [快速开始](quickstart.md) | [智能体集成](agents.md) | [运维](operations.md) | [部署](deployment.md)

Vitalis 报告从已保存快照读取事实、比较、分析和建议。缺失观测保持缺失；只有会改变当前结论的缺口才在对应位置提示。报告不要求用户回复，也不把投递状态当作健康反馈。

## 报告周期

| 类型 | 默认范围 | 重点 |
| --- | --- | --- |
| 晨报 | 目标日前一夜和可用晨间事实 | 先看睡眠，再说明当天重点；可选指标缺失不阻塞其它事实。 |
| 日报 | 目标本地日 | 保存分析时的睡眠、活动、训练、恢复、覆盖和版本信息，可审计、可回看。 |
| 晚报 | 目标本地日 | 面向阅读复盘当天活动和训练，给出明日重点；不替代日报完整快照。 |
| 周报 | 目标日所在周之前的上一完整本地周 | 解释持续变化及其主要来源，不把缺失日当休息日。 |
| 月报 | 目标日所在月之前的上一完整本地月 | 使用正确日均或频率比较方向，不只比较不同月长的总量。 |

周报默认周一至周日，月报按本地日历月。明确标记为 `rolling` 的结果才称“近 7 日”或“近 28 日”；不能把滚动窗口称自然周/月。`period_start`、`period_end` 描述统计范围，`as_of` 或生成时间描述数据看到的时刻。

日报内活动只能与相同截止时刻的历史比较；日内值不能直接和完整昨日比较后写成下降。睡眠、活动、训练和反馈分别保留来源、单位和可用日数。没有训练记录不等于休息日，未知动作不补名称，`12 / 10 / 8` 组次不改成三个相同组。

晚报发送前先同步，只汇总截至所示时间已经同步的训练和活动，不能保证训练已结束或当天记录已齐；开头明确说明未同步或之后的训练尚未计入。有明日建议时标明暂定，以次晨结合补齐的训练和昨夜恢复后的安排为准。迟到训练继续触发相关日期重算，已发晚报不自动重复推送。次晨分析与前一天已被渠道受理或送达的晚报所用快照比较，按来源和训练标识识别新增场次、时长或负荷等实测字段更新，在“昨天已记录的训练”中说明“较昨晚晚报补入/更新……，已纳入本次分析”。没有已确认受理的晚报、没有可比较的训练记录或记录未变化时不显示补录说明；不能把未发送、失败或投递不确定当作用户已经收到。补录依据、前后截止时刻、样本数和仅限已记录场次的覆盖范围保留在分析快照中。

## 阅读报告

### 先看什么

先看标题、日期和数据截止时刻，再看关键记录、变化和训练安排。晨报、晚报和日报以昨夜与当天为主，每个关键数字配一句个人参照：在近期范围内是“正常”，超出时是“偏高/偏低”或“偏多/偏少”，参照不足就写“无法判断”。这些判断来自已保存的分析，不由排版层另算。

晨报第一张卡是 0–100 准备度：70 是个人平常水平，60、75、85 是现有显示分段；同时给出影响最大的三个因素和 Zepp 晨起 Charge 的个人对照。这是产品的相对状态评分，不是医学上的合格线，计算规则见[数据合同](data-contracts.md#分析与报告)。

- 当天没过完的步数，不和完整一天比较后说下降。
- 训练负荷和步数的变化要说明变了多少；负荷另与前三周周均比较，骤增时提醒先别再加量。比较本身不另生成训练处方。
- 可选 HRV 缺失时可省略，不让一个缺项盖过其他有用事实；哪项比较缺数据，就在那一项说明。
- 28/60/90 天窗口、训练反应和个人关联放在周报、月报及 API；逐信号来源、覆盖和版本明细放在 API，不塞进日常推送。

### 数据不齐或正在更新时

推送和导出不用“排队、重算、快照”解释问题。只有影响阅读时，才在开头说明看到的是几点的数据、缺什么，例如“下面是截至 10-07 21:20 的数据；之后同步到的数据还没算进来。”仅事实版本要说明睡眠未到齐、同步未完成或发送较晚等实际原因，不给没有依据的训练建议。当天尚未过完不算数据缺失。

开发者可用 `GET /api/reports/{kind}/state` 或 Skill 的 `report … --state` 查看状态。JSON 保留版本、`analysis_run_id`、`data_quality`、事实、特征、趋势、事件和决策；`report_context.report_state` 区分当前、过期、排队、运行和失败，并提供同日期上一份成功结果 `last_good_snapshot`。旧结果不会冒充新结果。

### 各类报告的补充内容

- **跑步卡**：展示保存好的心率区间、心率漂移和近期相近距离的配速对照；相近距离不等于相同心率。
- **力量卡**：展示已记录组数、合格重量容量、肌群组数估算和下次候选方向，详见[力量训练卡](#力量训练卡)。不再用固定“休息三天”判定已经恢复。
- **本周负荷**：晨报列目标、进度、今天的份额及合资格的跑步分钟数；晚报列近 7 天与近 4 周周均的比值和已有状态。这不是伤病安全线。
- **模型效果回顾**：月报有相应结果时展示“系统对你的预测准不准”，比较模型与“明天和今天一样”的简单预测误差，并说明数据是否还在积累；它不是候选跑力已通过验证的证明。

Markdown 和保守的 inline HTML 从同一展示模型直接排版，不查数据库或重算健康指标，事实、单位、日期和缺口应一致。[合成报告示例](examples/reports/)由[生成器](../tools/generate_report_examples.py)生成，不手改。

### 周报与月报的变化摘要

周报“本周变化”沿用正文选定的同一组事实：睡眠比较平均时长，HRV 和静息心率比较选定来源的周中位数，训练负荷比较设备估算的整周总量。同一指标只给一条主要结论，不把不同设备的 SDNN、睡眠 HRV 或不同来源的日负荷中位数混写。睡眠恢复指标两周各至少有 5 天记录才比较；训练总负荷沿用两周训练清单与负荷记录的完整性要求。绝对变化不超过 5% 时不列入重点变化，具体数值仍保留在正文；这只是摘要筛选，不构成训练处方。所有分来源趋势、比较窗口、样本数和覆盖仍保留在分析与 API 中。

以上是周报已经采用的规则。月报摘要仍有多来源与正文统计方法不一致的已知问题，见[月报整理计划](plan/monthly-comparison-consistency.md)；不能把周报的验收结论直接套到月报。

## 训练教练建议

日报和晚报的单次训练卡显示已记录的主观用力程度，例如“RPE 7/10（Zepp 记录；越高越吃力）”。周报在训练汇总中列出已记录训练数、其中填写 RPE 的场次、来源、平均分及 8 分以上场次；没填的不按零分算，也不重复列反馈提交日的 RPE 均值。同一场训练在 Vitalis 补填或更正 RPE 后，按最新有效反馈更新。周内已评分训练平均达到 8 分时，建议下周把高强度训练隔开，其间安排轻松训练或休息；单次高 RPE 也作为力量训练调整的依据。评分只说明主观上吃不吃力，不当作运动成绩或身体恢复分。

已有训练的 RPE 随下一次覆盖该活动日期的 `workouts` 摘要同步补入，再按受影响日期重算；仅刷新运动详情不会补摘要字段。旧报告不直接读取原始响应或现场重算。字段来源、时间及覆盖口径见[数据合同](data-contracts.md)。

晨报把已保存的主要和可选训练展开为“怎么练”：力量写明重点部位、动作或动作模式、组数、次数、组间休息和每组保留余力；跑步写明热身、主体、冷身及可交谈程度或已有个人阈值支持的心率范围。沿用历史动作时保留原来的不同组次，不凭总组数补出动作，也不把未知负重口径展示成训练重量。可用时间较短时，力量按工作组与休息的估算预算减少工作组或动作，不压缩休息；这些是计划估算，不是已完成训练事实。跑步分步时长与总时长一致，长跑不以固定下限覆盖近期个人时长，周负荷份额也不能放大已经下调的跑步剂量。进阶条件和停止条件随训练显示；可选安排注明二选一或至少间隔 6 小时。只有事实的报告和历史补发不展示训练处方。

力量轮换先看已识别的分化，再看各肌群最近训练与明确酸痛记录。原定动作涉及最近两天练过或仍有明显酸痛的肌群时，改用记录中可识别且没有这些冲突的其他部位；没有合适动作就安排恢复活动，不能一面提示避开、一面继续安排同一肌群。距上次训练的天数只是安排参考，不代表已经确认恢复。晚报在明确动作支持下展示当天练到的部位、已识别分化和暂定的下次轮换候选，最终安排以次晨补齐数据后的恢复决策为准。

周报按“力量”和“跑步”说明本周做了什么、下周怎样安排，可见建议只展示已保存的标题和行动；证据窗口、课型统计和覆盖等 `reasons` 仍保留在分析快照及 API，不逐项附在建议后面。恢复、疼痛、负荷或记录缺口只说明实际触发的限制，同一原因解释一次，不把它们混写成同时存在的问题；恢复事件已有好转时明确说明，尚未解除的限制仍约束安排。去重只移除已被具体建议覆盖的内容，不能因为显示跑步建议而删除尚未覆盖的力量目标。

肌群覆盖统计报告周内合资格的明确动作涉及的训练天数，复合动作可能计入多个部位；这不是有效组数或重量容量，未识别的部位保持未知。Zepp 的动作名称映射本身不保证动作或处方资格；另有已核对的人体图区域时，可以展示带来源的部位参与估算，但不能称为用户确认或实测肌肉受力。只有名称而没有部位依据时，才说明暂不能判断练了哪些部位；不把已经同步的明细写成同步失败。详见[力量数据说明](data-contracts.md#力量容量肌群和单次回顾)。

分化根据设置的每周力量次数给候选：2 次全身 A/B，3 次上肢／下肢／全身或全身交替，4 次上下肢交替；已有高可信三分化或五分化时保留轮转，不要求自然周内完成一轮。没有次数偏好时只根据已记录训练日给候选，不替用户写入偏好。建议只给顺序，按可用日与实际时间顺延，不为漏训补课或追赶负荷。

跑步以能交谈的轻松跑为主；经验未知或初学者不新增阈值间歇、稳定跑或自动加长长跑。每日质量课还需明确中高阶经验、已有训练基础、个人阈值与无疼痛记录，并服从恢复、负荷和训练间隔门控；周报只在近 28 天训练覆盖完整且已有明确质量课习惯时，建议恢复允许下至多维持一次同类质量课。较长跑、质量跑与较重下肢力量之间留轻松或休息日。训练覆盖、动作覆盖或恢复条件不足时，周报只汇总已有训练并说明为何暂不编排。

建议设计参考了 [healthy-fitness-coach-skill](https://github.com/Surge-Dan/healthy-fitness-coach-skill) 的按频率选择分化与渐进原则，以及 [running-coach-skill](https://github.com/liumy-qd/running-coach-skill) 的先检查恢复条件、再生成并核对训练安排的思路；报告引擎不运行这些 Skill。Hermes 另已接入 knowledge-only 的健身教练适配包，范围和来源见[智能体集成](agents.md#教练知识-skill)，不参与服务器报告计算；未接入 running-coach 工具。训练依据仍来自 Vitalis 的证据目录及 [ACSM 2026 力量训练指南](https://acsm.org/resistance-training-guidelines-update-2026/)、[WHO 身体活动指南](https://www.who.int/publications/i/item/9789240015128)和 [NHS 初学跑步方案](https://www.nhs.uk/live-well/exercise/get-running-with-couch-to-5k/)。

## 力量训练卡

力量卡只展示已经保存的结果，分清三件事：

1. **做了多少**：总记录组数，以及主要练到、辅助参与的肌群组数估算。缺重量仍可有组数；同一组涉及多个肌群，不能把各肌群数字相加当总组数。
2. **重量容量**：重量、单位、负重口径和次数明确时，展示重量乘次数；它不要求先识别肌群，也不是把重量分摊成肌肉受力。单手、总重和器械标称口径分别说明。估算 1RM 另有动作和用力资格，不能自动称为个人纪录。
3. **下次怎么安排**：列建议方向、上次集中训练日期和一条热身调整条件；相近候选可并列，没有候选就显示限制原因，不要求先补齐重量或反馈才给方向。

来源说明一次。近期累计量、个人参照、辅助参与折算和完整历史留在分析明细，不逐项塞进推送；每场训练最多附两条有依据的改进。报告排版不临时重算容量、1RM 或肌群关系。

数值总分和合成跑力尚未通过验证，不进入日常报告或训练强度建议；缺关键数据就说明缺口，见[评分规则](data-contracts.md#单次训练评分的共同规则)。

## 本地导出与 API

从仓库根目录、已有 demo 数据库执行：

```powershell
uv run --locked --extra dev vitalis report daily --user demo --day 2026-10-07 --format markdown --output .\daily.md
uv run --locked --extra dev vitalis report evening --user demo --day 2026-10-07 --format html --output .\evening.html
```

导出是纯预览，要求输出路径不存在。HTTP 使用 `GET /api/reports/{kind}?day=YYYY-MM-DD` 和 Bearer 令牌读取已保存快照；GET 不启动同步或分析。没有快照返回 404。API 的 `daily` 返回完整 `DailyProfile` 事实快照，`evening` 返回面向阅读的晚报投影；还提供 `weekly-briefing` 和 `monthly-briefing` 的读取路径，字段以 `/openapi.json` 为准。

## PushPlus

PushPlus 是单向、只读的推送出口。推送使用 `html` 模板：深色页头写明报告类型、日期、数据截至和晨报的训练安排标签；关键记录是数值卡片，相对个人参照的变化以“↑/↓ 百分比”文字标出，颜色只按指标方向（HRV、睡眠、步数升高为好，静息心率、压力升高需留意）作辅助；各节事实按“名称 / 数值”对齐，日内压力分区画成一条带文字图例的比例条，今天的重点/明日重点用浅色卡片。消息不能附带样式表，所有颜色都写在元素上；CLI 导出和 API 仍可选 Markdown。消息模板必须与正文类型一致。HTTP 200 只表示 HTTP 请求完成；只有业务 `code=200` 且返回有效供应商消息标识时才记录 `accepted`，业务失败不能记为 accepted。最终送达、失败和未知分别记录；超时或响应丢失保持 `uncertain`，不盲目重试。投递记录不会改变目标完成、反馈或健康状态。配置了 `VITALIS_PUBLIC_URL` 时，晨报和晚报末尾附一次性反馈链接，链接篇幅计入运输预算；反馈页的规则见[运维](operations.md)。

PushPlus 拒绝超过 2 万字的单条正文（业务 `code=999`「发送内容过大」）；HTML 正文按转换后的可见文本计阅读预算，Markdown 按其转换成的 HTML 计运输长度（每段都会加标签），推送渲染因此设独立的 18,000 字运输预算（UTF-16 字符计）。晨报、日报、晚报、周报和月报的可见文字上限分别为 8,000、10,000、10,000、12,000、14,000 个 UTF-16 字符，防止长历史把阅读正文撑大；可见上限与运输预算分别计算，显式运输上限不能绕过可见上限。日常报告通常远低于这两个上限，预算只是兜底：未超出时正文与完整渲染一致；超出时按区块公平分配篇幅，区块标题、关键记录和今天的重点/明日重点始终保留，变化优先于明细，每个训练动作与其组次和对照整体保留或整体省略，区块末尾注明省略数量，文末提示完整报告的读取方式。超过上限的正文在发送前判为失败，不发起请求。API、CLI 导出和 Hermes 仍读取完整报告。

本地浏览器预览不等于 PushPlus 实际接收端验证；改动推送版式时，用测试补发把一份真实报告发到接收端，确认效果后再部署（2026-10-10 起按此执行）。发送前应检查实际 `content` 是否被代码围栏、JSON 二次序列化、字面量换行、错误模板或整体 HTML 转义包裹。用户备注和动作名称必须安全转义。

## Hermes

Hermes 是可选的对话入口，不是报告生成依赖。默认先短答用户当前问题；只有缺少关键输入时才追问。只有用户明确意图和授权成立时，才通过独立反馈或目标用例写入；发送、打开、沉默和未回复都不改变目标或健康反馈。接入方式和当前验收范围统一见[智能体集成](agents.md#验收边界)；离仓 mock 测试、本地合成数据对话和服务器真实用户接入是不同层次，不能互相替代。

## 调度与状态

晨报、晚报、同步和可选周/月报都由独立 worker 负责；调度时间、时区和启用开关的唯一配置说明见[运维](operations.md)。投递成功、失败、延期和不确定状态与分析快照分离；迟到数据只刷新尚未发送且仍合资格的意图，不把样式更新当成历史补发。

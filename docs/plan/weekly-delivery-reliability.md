# 重启错过周报，也能补上并留下漏发记录

[改动计划](README.md) · P1 · 状态：待开发，补发期限待明确

## 现在是什么情况

**如果服务恰好在周报发送时间停了，现在可能既不补发，也不留下“这期漏了”的告警。**

现有周报定时器只记在运行中的 worker 里。跨过发送时刻再启动，它只会等待下一次；已有的补偿只覆盖晚报，缺少投递任务时的到点告警也只覆盖晨报和晚报。

2026-10-19 的历史排查还发现生产配置没有开启周报，当天已开启。但“开关打开”不等于自动投递验收完成，更没有解决跨重启补偿。当前行为及排查步骤见[周报没有收到时](../operations.md#周报没有收到时)。

## 接下来做什么

1. **先定补发规则**：按部署时区明确周报应何时发送、最晚允许补到何时、过期后怎么处理，不借用晨晚报的期限。
2. **启动后检查缺失**：worker 启动和定期检查时，按用户和报告周核对同步、分析和投递任务。仍在期限内且确实缺失时，补建原来的流程。
3. **补的是原来那一周**：保留原报告日期范围和投递意图日期（周报结束日），不能按补偿当天重新确定报告周；仍经过同步、分析、保存报告和发送队列，不直接拼报告外发。
4. **漏发要有原因**：区分没到时间、开关关闭、没有投递目标、来源未授权、同步未完成、分析失败、没有报告和没建投递任务。到期仍缺失时，独立告警检查也能留下记录。
5. **不能重复发**：已有进行中任务继续等待；已经受理、已经送达或不知道是否送达的消息，不因重启再发一遍。

## 怎样算完成

- 用可控时钟测试到点前启动、运行中稍有延迟、跨发送时刻重启、过期后启动及下一周才启动；日期、时区和补发范围都正确。
- 多个检查同时运行、反复重启、同步失败、分析失败或缺合格报告时，每个用户每周最多一条投递意图；已受理或结果不确定的消息不重发。
- 周报关闭、未到时间时不报“预期漏发”。超过期限的缺失即使 worker 没运行，也能由独立告警进程记录，并通过 `GET /api/delivery-alerts` 和 `GET /api/deliveries` 查询。
- 调度、同步、分析队列、投递和告警测试，以及 `uv run --locked --extra dev python tools/check.py backend` 通过。
- 上线后观察一次真实自动定时链路，或经授权的跨重启补偿：同步、分析、正确日期的报告、唯一投递记录和渠道受理标识齐全。手动推送或只有周报快照都不能替代；渠道受理不等于用户收到。

## 开发时注意

- “投递意图”是数据库里的一条待发送任务；“outbox”是发送队列；“幂等”指多次检查不会创建多份任务或重复发送。
- 周报分析任务保留 `delivery_period=weekly`；已有任务的租约、执行权检查和失败重试规则继续有效。
- 过期后保留漏发证据；人工补发另记，不能把原自动流程改成成功。
- 本项只完善补偿与数据库告警，不接入[第二提醒通道](delivery-alerts.md)。

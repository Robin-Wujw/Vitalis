# 报告漏发时，要不要用另一个渠道提醒

[改动计划](README.md) · P2 · 状态：等待用户选择，暂不开发外发通道

## 现在是什么情况

**系统已经会记录故障，但用户还要自己查询，才知道报告漏了。**

现有独立告警进程能在 worker 卡住时继续检查漏发、分析失败和心跳异常。worker 自己另把数据停更、Zepp 凭据失效写进同一张告警表；这两类检查仍依赖 worker 运行。当前没有把这些告警发到第二个渠道，范围和查询方法见[运维告警说明](../operations.md#投递目标与告警)。

用户在 2026-10-13 选择暂时只记录，10-14 再次确认。本项等待新的明确选择，不默认接入邮件或聊天，也不因为 Hermes 能聊天就自动开启告警。

## 接下来做什么

1. 用户决定是否需要主动提醒；若需要，再选择不依赖 PushPlus 的渠道：
   - **邮件**：由独立告警进程发送，需要配置 SMTP 和私密凭据。
   - **Hermes**：由 Hermes 定时读取 `GET /api/delivery-alerts`，再发到用户选定的聊天渠道。
2. 选定后再实现发送记录和重试：新事件只通知一次，失败保留待重试，已确认送达的不再发送。响应不明确时先保留不确定状态，不盲目重复发送。
3. 保持告警检查与报告 worker 独立，不能依赖已经卡住的进程来报故障。

## 怎样算完成

- 用户已明确选定渠道和接收目标；凭据不进入源码、命令参数、日志或示例。
- 合成测试覆盖成功、失败后重试、重复检查及响应不明确，同一事件不会重复提醒。
- 在目标部署环境，经用户授权使用隔离测试实例或约定维护窗口，模拟 worker 心跳超过 30 分钟不更新，确认测试目标收到告警；不擅自停正在使用的服务做演练。
- 外发结果有记录，失败原因可查询。用户仍选择暂不接入时，保持等待状态，不声称已经实现。

## 不在本项内

[周报可靠性](weekly-delivery-reliability.md)负责补建漏掉的周报流程，并补齐相应数据库告警。本项只转发已经存在的事件，不代替周报检测，也不自动重发健康报告。

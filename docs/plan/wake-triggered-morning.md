# 连续一周确认晨报没有提前发

[改动计划](README.md) · P0 · 状态：规则已有，等待上线后的实际验证

## 现在是什么情况

**要确认的是：晨报不会拿半截睡眠当整晚睡眠，也不会在人还没起床时就开始生成。**

原验收记录中，2026-10-25 和 10-26 都出现了半截睡眠上传被提前放行的问题。现有代码已经要求：醒来满 60 分钟后再读取，而且同一次返回里的睡眠和设备数据都必须足够新。若后来发现继续睡了，会继续等待并重新分析。具体规则见[晨报运行说明](../operations.md#配置主责)。

这只能减少“读到旧上传”的问题，不能保证 Zepp 已经识别出所有续睡。仍需观察真实手机上传和实际接收时间。

## 接下来做什么

1. 从修正规则实际上线后开始，收集连续七天记录，不沿用旧规则下的观察天数。
2. 逐日对照最终醒来时间、睡眠探测次数、晨报同步开始时间、所用分析结果、投递状态和用户收到时是否已起床。
3. 对提前、迟到、漏发和等到窗口结束才发送的日期分别查原因：手机没上传、Zepp 没识别续睡，还是服务处理慢。
4. 发现问题先记录原因再修正；不能用“睡得够久”或“有心率”推断已经醒来。

## 怎样算完成

- 七天每天都有可核对的结果；缺一天的报告或睡眠依据，不能算完整验收。
- 没有半截睡眠触发，也没有醒来不足 60 分钟就开始的晨报；窗口结束后的兜底发送单独核对原因。
- 检查工具的 `passes` 为真，所有异常和兜底都有解释，用户确认收到时已经起床。
- 完成实际观察和用户确认后才关闭本项。仅代码测试通过不算完成。

## 核查时用什么

```bash
uv run --locked --extra dev vitalis wake-check --user <用户> --days 7 --end <验收结束日>
```

注意：`wake-check` 的 `report_created_at` 是**投递任务建立时间**，不是手机收到时间；`passes` 主要检查提前触发和延迟中位数，不保证七天每天都成功投递。必须另外逐日核对投递状态，渠道“已受理”也不等于最终送达。

实现入口：[醒来检查](../../src/vitalis/application/wake_check.py)、[睡眠结束判断](../../src/vitalis/intelligence/sleep_completion.py)。数据库争用另见[同步计划](sync-write-transactions.md)，不要未经排查就把所有延迟归到数据库。

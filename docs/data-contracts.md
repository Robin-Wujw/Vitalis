# 数据合同

[文档中心](README.md) | [当前架构](architecture.md) | [Zepp](zepp.md) | [报告与渠道](reports.md)

本页说明进入分析和对外报告的事实资格。字段的完整类型和版本以 `src/vitalis/domain/models.py`、`src/vitalis/intelligence/contracts.py` 和运行服务 `/openapi.json` 为准。

## 事实与来源

规范事实至少保留用户、来源、来源范围、设备（如有）、单位和观测时间。健康观测、厂商日指标、训练摘要、训练明细和用户反馈是不同类型，不能因为字段名称相似就合并。分析结果还保留 `analysis_run_id`、schema/intelligence/decision/evidence 版本和生成时间。

数据集的 `source_mode` 与供应商 `source` 独立：真实、合成和离线回放分别为 `real`、`mock`、`replay`。用户数据集首次声明后不能换模式；改用独立用户或数据库。同步请求冻结模式并纳入幂等身份，执行模式不一致时拒绝请求。报告的 `report_context.source_mode` 来自保存的输入标签，不根据当前配置反推；未标记输入显示 `unknown`。`replay` 标签只表示显式离线输入，本项目尚未实现完整原始响应回放系统。

常用单位如下：

| 字段 | 合同单位与语义 |
| --- | --- |
| 睡眠时长、深睡、REM、浅睡、清醒 | 分钟；零和缺失不同。 |
| 步数 | 步；只在来源明确观测时出现。 |
| 活动/训练时长 | 分钟；训练摘要和活动时长不是同一指标。 |
| 距离 | `km`；没有单位或转换依据时不计算容量。 |
| 心率 | `bpm`；HRV 的 `value_ms` 是毫秒。 |
| 训练负荷 | 厂商负荷或明确算法字段；不能当作通用能量单位。 |
| 重量 | 优先 `weight_kg`；原始单位不明时保留未知，不把数值猜成公斤。 |
| 次数、组数 | 次数是每组或记录明确给出的 repetitions；组数只在真实组次有依据时出现。 |

时间戳通常以 UTC 保存，报告按配置时区（默认 `Asia/Shanghai`）解释本地日。日内区间使用明确截止时刻；跨日睡眠按解析后的本地报告日期归属。`period_start`/`period_end` 是包含端点的本地日期范围，`generated_at` 是生成时刻，`as_of` 表示数据看到的时刻。

## 缺失、零和不可比

- 缺失字段保持 `null`、空列表或明确不可用状态；绝不补零、拿旧快照填充或把未知训练日改成休息日。
- 零只有在来源明确报告零时才成立。没有步数记录不是零步，没有力量明细不是零组。
- 来源、设备、单位或时间口径不同的记录不直接比较；同一用户历史也必须满足相同截止时刻和资格条件。
- 可选 HRV、密集文件或动作详情缺失只影响相关特征，不阻塞整份报告。必需信号不足时使用 `INSUFFICIENT_DATA`，不提供对应推断或处方。
- `observed_fields`、coverage、`sample_count`、`distinct_days` 和 `limitations` 解释观测覆盖；它们不是伪造的测量值，也不自动代表数据质量概率。
- Open Health 的 42 天训练负荷只使用持久同步账本验证的日期。完整窗口、分页和预算都合格时才设置 `upstream_coverage_verified`；未验证日保持 UNKNOWN。有训练但缺心率明细仍不可评分，摘要截断不会把遗漏训练改写成休息日，训练和心率输入遵守 `as_of`。
- 分析 profile 对高频样本执行每指标和整档预算；达到预算时保留已读取事实并写入质量标记，coverage 必须按部分数据解释，不能把截断样本称为完整历史。

## 分析与报告

Daily、Morning、Weekly、Monthly 和 briefing 投影共享同一分析快照，但展示顺序不同。日历周为周一至周日的完整周，日历月为完整本地月份；滚动窗口必须标记 `period_mode=rolling`。月报的日均、有效日数和频率要使用正确分母，不以不同月长的原始总量直接判断改善。

比较应就地标明窗口、基线、单位、有效日数和来源。`association` 只表示个人统计关联，不表示因果；厂商睡眠分数、readiness、Charge 等按来源标签描述，不替代 Vitalis 的决策状态。`open_health_insights` 是描述性 `shadow_only` 输出，不改变 `decision`。

力量训练记录保留动作名称、来源、单位、真实组次和每组次数。`12 / 10 / 8` 不得改写为 `3 × 10`；设备识别与用户确认分别标记，没有冲突的有效设备记录可直接展示，但不能声称用户已确认。未知动作不能推断为某个动作，未知重量不能计算容量。

用户反馈必须由用户明确提供。RPE 需要关联已完成训练；`workout_id` 与 `workout_source` 必须成对出现。反馈、推荐完成、事件确认和训练确认是独立写入，不由 PushPlus 发送、打开、沉默或 Hermes 未回复触发。

## API 与写入

所有用户范围 API 使用 Bearer 令牌；`X-User-Id` 只做一致性检查。GET 报告和查询只读已保存结果，不启动同步或分析。`POST /api/analysis-runs` 与 `POST /api/sync-jobs` 返回任务受理信息，写请求使用 `Idempotency-Key`；需查询 `GET /api/jobs/{job_id}`，直到 worker 保存结果。

资料 patch 使用当前 revision，遇到冲突先重新读取。Skill 的幂等文件记录请求指纹；响应不明确时复用同一个文件，不能创建新键盲重试。原始反馈通过标准输入传递，令牌、健康记录和真实凭据不能进入 URL、日志、样例或快照。

## 校验失败如何处理

无单位、无来源、时间冲突、非法范围、跨用户或已撤销来源的记录应拒绝或保持不可用，并记录可诊断的非敏感原因。解析器不能把厂商未知枚举映射成已知动作；新增映射要补协议证据和回归测试。修改合同时同步更新 `tests/`、生成 API 参考和本页，不通过删除约束来让检查变绿。

# 核对力量动作、重量和候选评分

[改动计划](README.md) · P1 · 状态：分析功能已有，待真实案例审核；总分未启用

## 现在是什么情况

**系统能统计力量记录，但还要确认“这是什么动作、重量怎么算、评分是否合理”在真实使用中靠得住。**

已有功能包括重量乘次数的训练量、肌群组数估算、最近 180 天个人参照、可并列的下次训练方向，以及单次训练回顾。不是从零开发一套力量模型；当前规则见[力量数据说明](../data-contracts.md#力量容量肌群和单次回顾)。

动作目录中的名字和人体图参考，不等于用户已确认动作，更不等于测到了真实肌肉受力。候选评分只是内部试算，公开总分仍为空。

## 接下来做什么

1. **先查常用动作**：在私有环境抽查实际记录，核对动作、同名器械变式、用户纠错、人体图区域和每组顺序。缺少文字解释的区域先补证据，补不到就保留未知。优先审核用户实际练的动作，不为凑覆盖率按名称猜全目录。
2. **把重量含义问清楚**：分别验证单只与双只哑铃、器械标称重量、辅助重量、自重、左右侧，以及热身组和正式工作组。缺信息就保留未知，不补零、不自动乘二。
3. **检查下次安排是否合理**：用较长历史核对“哪次算集中练过”“历史参照是否有代表性”“辅助参与折算改变后会不会推荐不同方向”。对晚到数据、反馈更正和映射更新检查是否重复计组或重复推送。
4. **单独审核评分**：准备维持、减量、未完成、高努力、自重、缺余力信息和明细不全的案例。补专门回归测试，再核对真实案例是否尊重事前目标，而不是鼓励加重、加组或力竭；现有简单候选公式不等于成熟的逐组评分。
5. **再决定启用范围**：先让用户看真实预览，保留不通过的动作和案例。正式展示总分需要后续明确的代码变更和发布，不能靠改文档开启。

## 怎样算完成

- 常用动作和重量含义有可审阅的依据，未确认区域继续显示未知；厂商参考不能提高“用户已确认”的覆盖率。
- 明确哪些记录可以统计正式工作组，哪些只能说明练到过这个部位；单侧记录不重复计算。
- 近期安排在代表性案例中合理，映射或反馈更新不会重复计数、重复推送。
- 评分案例、容差、固定权重、规则版本、未通过项及允许展示的范围有记录；不符合条件的场次仍无总分。
- 目录、解析、保存、数据加载、力量分析、周报、决策、报告和通知的目标测试，以及 `tools/check.py backend`、`docs`、`package` 和 `git diff --check` 通过；命令使用锁定的 `uv run --locked --extra dev python` 环境。
- 实际预览与发布验收完成。合成测试不能代替上述真实案例审核；不为显示映射而备份、换库或改写原始记录。

## 审核时要分清的词

- **RPE**：整场主观上有多吃力；**RIR**：某组结束时估计还能做几次。整场 RPE 不能代填每组 RIR。
- **容量**：明确重量 × 次数，不等于肌肉刺激或训练收益。
- **肌群组数估算**：根据动作判断主要练到和辅助参与，不是手表直接测量。辅助组的折算系数是粗略比较方法。
- 估算力量只在用力程度可比时比较，不能把“更接近力竭”解释为“力量变强”。逐组或明确范围的 RIR 输入也要实际验证。

跑步和力量共用的事前目标、40/40/20 候选权重和缺数据处理，统一见[单次训练评分规则](../data-contracts.md#单次训练评分的共同规则)。动作证据见 [Zepp 目录](../zepp.md#同步与任务)，展示规则见[报告与渠道](../reports.md#力量训练卡)。

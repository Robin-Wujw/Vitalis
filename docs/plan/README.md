# 改动计划

[文档中心](../README.md) | [仓库规则](../../AGENTS.md) | [发布与部署](../deployment.md)

这里记录**还没完成的工作**，包括待开发、待实际验证和待用户选择三类。功能写好了，不代表真实使用已经验证通过；日期到了，也不代表可以自动关闭计划。

## 先看结论

Vitalis 已有从 Zepp 取数、分析、保存报告，再通过 API、PushPlus 和 Skill 读取的完整链路。当前重点不是重做这条链路，而是：

1. **先确认每天能正常用**：晨报是否在起床后发送；网页登录、历史数据回填和重新登录是否可靠。
2. **修复已知薄弱处**：同步时不要长时间占住数据库；服务重启不能悄悄漏掉周报；月报摘要不能和正文说反话。
3. **验证后再开放评分**：力量训练先核对动作与重量，跑步先用独立成绩检验预测。候选分数不能直接当训练依据。
4. **保留用户决定**：第二告警通道暂不接入；反馈入口等用户实际提交，页面的完成提示问题另行修正。

本次整理依据仓库文档、源码和测试，不是服务器巡检。下面提到的历史上线记录不代表本次已重新验证；没有实际结果的项目继续保留。

## 怎么看优先级和状态

- **P0：优先处理**，关系到日常使用是否正常。
- **P1：随后完善**，修复可靠性、内容一致性和训练判断的缺口。
- **P2：可后置**，等待选择或配合后再推进。

优先级不是交付日期。每项都有“现在是什么情况、接下来做什么、怎样算完成”；涉及代码的细节放在文末，不用先读术语才能理解目标。

## 项目之间的关系

- 周报计划负责**发现漏发、补建任务和记录原因**；第二通道计划只负责**把已有告警通知用户**，两者不是同一个功能。
- 晨报计划验证发送时机；同步事务计划处理数据库争用，不把所有延迟都归到同一原因。
- 跑步和力量共用[单次训练评分规则](../data-contracts.md#单次训练评分的共同规则)，但能力预测、动作识别和各自的实际案例必须分别验证。

## 怎样维护

- 一项工作只保留一份计划；当前行为和长期规则写进[对应指南](../README.md#主题归属)，计划只写剩余差距。
- 按完成条件逐条留证据。测试通过、功能上线、渠道受理和用户实际收到是不同结果，不互相代替。
- 用户能看到的报告内容或版式变化，按[发布流程](../deployment.md)先私下提供真实预览确认；真实记录、凭据和原始响应不提交到仓库。
- 实现、必要的实际验收和发布完成后，删除计划文件及本页对应行。历史查 git；新发现的问题另建条目，不保留“已完成”清单。

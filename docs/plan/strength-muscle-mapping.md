# 力量动作肌群映射、容量估算与下次训练推荐

[改动计划](README.md) · P1 · 相关：[跑力与单次评价方案](running-performance-model.md)、[数据合同](../data-contracts.md)、[Zepp](../zepp.md)、[报告与渠道](../reports.md)

## 目标与现状

2026-10-20 调研方案，尚未实现。根据逐组记录估算本次和近一周训练量，解释最近练了哪些部位，推荐下一次优先肌群，并评价每次训练是否符合个人目标。将来源事实、运动知识推导和可执行建议分层；允许有依据的估算，但不能把估算写成测量或用户确认。

当前 Zepp 动作目录的 1,133 个 `canonical_exercise_id` 都为空，生成器只保留 `actionType/actionName/selfWeightType` 等字段。这仅证明当前提取结果没有主次肌群，不能据此断言 APK 或原始配置没有映射。

现有实现还存在需要同时解决的边界：`EXERCISE_KNOWLEDGE` 依赖名称子串，可能把“俯卧弹力绳腿弯举”归为肱二头肌；容量计算依赖动作与肌群识别，导致部分可计算负重记录也不可用；容量按系数分摊到肌群；任意次数套 Epley 估算 1RM；`_next_focus` 固定循环；肌群负荷比直接生成 `PRODUCTIVE/OVERTRAINING`。这些都不足以支撑新的健康建议。

## 一、APK 核查：已证实与待补证据

本次对用户提供的 Zepp 10.8.7-play APKM 进行静态检查，不运行 App、不访问个人账户、不修改原文件。已核验 APKM SHA-256：`64e1d87b6ab79e0ecedfbead176cc6bb781f9754b46915d52c0d2ccfbcef5949`。

| 证据 | 结论 |
| --- | --- |
| `StrengthTrainingAction` 有 `int[] mainPositions` 与 `int[] subPositions` | 动作对象有主要与次要部位映射字段，不是 bitmask 或负荷系数 |
| `StrengthTrainingUtils.s(JSONObject)` 解析两数组；`i(List)` 按 `actionType` 查找 | 映射来自 `/sport/config/muscle` 配置，并关联动作代码 |
| `r121.t0` 把两数组交给 `STBodyPositionView.c(main, sub)` | 该映射实际被人体图消费，不只是未使用的文本 |
| `STBodyPositionView.a()` 用 `st_body_<编号>.webp` 分别着色 | 数组值是 46 个人体图区域 ID，不能直接当作标准肌肉代码 |
| `StrengthTrainingUtils.l()` 解析另一配置的 `actionUpLevelList` | `levelId/levelName/actionTypeList` 是独立菜单分组，与人体图数组不是同一套编号 |

菜单类别是肩颈、胸、腹、上背、下背、手臂、臀、腿；`t121$c.e → cvk0.a → bvk0` 选择类别图标。菜单 ID 5 是下背，而人体区域 ID 5 位于胸部图层，直接混用会严重误映射。未找到人体区域的官方解剖名称；不能据图自动声称已经核验腘绳肌、股四头肌等精细关系。

目录的正式默认地址由 `f9d1 → hy10` 确认为 `https://api-mifit.zepp.com/sport/config/muscle`，`ah10.f` 支持动态域名替换。本次不带凭据访问该地址及三个已记录旧域名均返回 HTTP 401；正式地址错误为 `invalid token / 0102`。没有重新取得完整目录，之前的目录摘要也未重新核验。因此，动作名称的 1,133 项覆盖不能当成肌群映射覆盖率。

解析链先将远程响应保存在 `strength_training_keep/strength_training`，再构造动作对象；菜单使用单独的 `strength_training_group` 缓存。APK 常见文本 assets 中没有发现这两个字段，但此扫描不能排除其他嵌入形式。准确结论是“APK 有消费动作—主要/次要部位映射的完整代码链，常规路径读取远程配置”，而不是“已从 APK 解出全部静态肌群表”。

## 二、基础力量训练知识怎样进入模型

| 研究依据 | 支持的设计 | 不应推导出的结论 |
| --- | --- | --- |
| ACSM 2026：137 篇系统综述、超过 30,000 人 [S1] | 健康成人规律训练主要肌群；按健康、力量、增肌目标调整剂量，重视可持续参与 | 所有人每块肌肉必须每周十组、每组力竭或每周自动加量 |
| Pelland 2026：67 项研究、2,058 人 [S2] | 区分直接与间接组数；间接按半组计的方法在该分析中获得较强支持；剂量收益递减 | 辅助肌群恰好承受 50% 重量或获得精确 50% 刺激 |
| Robinson 2024 接近力竭荟萃回归 [S3] | 接近力竭程度可能影响增肌，但其连续关系仍不确定，力量与增肌反应不同 | RIR 缺失就按力竭算，所有记录组都叫“有效组” |
| Schoenfeld 2019 频率荟萃分析 [S4] | 等周训练量时，频率对增肌的独立影响较小，可按习惯安排分化 | 五分化必然优于全身训练，固定 48 小时已完成恢复 |
| Nuzzo 2024 次数—%1RM 荟萃回归 [S5] | 动作与个体差异影响次数和最大力量关系，需要体现不确定性 | 任意器械、任意高次数的 Epley 值都是精确 1RM |
| Schumann 2022 并行训练荟萃分析 [S6] | 有氧与力量总体未必损害最大力量和增肌；同场训练更可能影响爆发力适应 | 跑步必然掉肌肉，每个人必须间隔固定小时数 |
| Saw 2016 训练反应系统综述 [S7] | 主观反馈有独立价值，应与客观记录结合 | HRV 或厂商准备度可代替局部酸痛和动作完成情况 |

调研日期 2026-10-20，通过 Europe PMC 核对来源；[S1] 读取全文，其余核对摘要。研究主要针对健康成人，部分样本以年轻男性为主，不能直接迁移为伤病康复处方。以下估算口径、门槛和权重是待验收的产品设计，不是论文已验证的 Vitalis 算法。

## 三、容量按信息完整度分层

| 输出 | 最低信息 | 方法 |
| --- | --- | --- |
| 记录组数、次数 | 可信组序、实际次数 | 保留 12 / 10 / 8，不写成 3 × 10；时长型动作另记秒 |
| 已知外部负荷容量 | 每组重量、单位、负重口径、次数 | `Σ负荷 kg × 次数`；只合计口径明确的组并注明覆盖 |
| 肌群直接/间接组数 | 可信动作记录、审核过的肌群关系 | 分别统计各肌群工作组；重量缺失不妨碍组数统计 |
| 肌群等效组数 | 上述组数、估算规则版本 | `直接组 + 0.5 × 间接组`，标为粗略估计 |
| 力量表现趋势 | 同动作变式、器械/负重口径、可比组 | 优先同重量次数、同次数重量和明确 RIR；有条件估算 1RM |

### 重量与身体负荷

- 区分杠铃总重、单只哑铃、双只总重、器械标称重量、自重、附加负重和辅助重量。明确“两只同时各 10 kg”才换算 20 kg，不从“哑铃”两字自动乘二。
- 器械标称 kg 可在同台/同配置下记容量，不能当真实肌肉受力或与另一台滑轮器械直接比进步。公斤容量不是机械功，后者还需要位移。
- 辅助引体等记录的辅助 kg 是减轻负担的设置，不计作正向外部负荷容量；同条件减少辅助可单列为表现变化。自重动作的附加负重可单列“附加负重容量”，但不代表完整身体负荷，也不能混入自重总容量或据此估算整体 1RM。
- 动作暂不明确，但物理重量、口径和次数明确时，仍可计算该记录的外部容量；不能据此判断肌群或与某规范动作比较。将“能算重量”与“能判断部位”拆开，避免一个缺口遮住全部信息。
- 按口径展示已知容量；跨动作的全场合计仅作账面记录，不用来判定腿日一定优于胸日。更换动作组合后不能直接用总吨位涨跌判断进步。
- 自重动作先观察组数、次数、动作难度和明确 RIR，不写成 0 kg 容量。若后续采用 `等效负荷 = 体重 × 动作系数 + 附加负重 − 有效辅助`，必须另存模型估计、系数依据、适用动作、体重日期和区间，不混入记录容量。支点、身体比例和辅助器械改变口径，首期不设通用体重百分比。
- 单侧动作保留左右侧。每侧三组表示左三、右三，不变成单侧六组；负重容量按实际完成侧次计算，肌群剂量按同一侧规则汇总。左右未知不自动翻倍。

### 肌群训练量

复合动作可给多个主要肌群各记一组直接组，辅助肌群各记间接组。这是各肌群的训练暴露，不要求肌群组数之和等于全场组数。不能把公斤容量分成“胸吃了 60%、三头吃了 20%”并称为实际受力。

建议显示“胸：直接 6 组”“三头：直接 2 组＋间接 6 组，约 5 等效组”。0.5 有 [S2] 的建模支持，仍需做 0、0.5、1 的敏感性分析；系数改变就会翻转下次推荐时降低结论强度，不称某部位必然欠量。

热身、工作组、技术练习和力竭组分开。明确热身不进入工作组估计；用途未知时保留“类型未知的训练组”，不因重量轻就判为热身。缺少逐组努力信息时不称“有效增肌组”；整场 RPE 不等于每组 RIR。时长型与重复次数分开，不把平板支撑一分钟换算成若干次。

### 覆盖分别报告

每场保存总记录组数、厂商摘要组数（若有）、明细完整性、动作映射组数、可算负重组数、可算肌群组数、明确工作组数和 RIR 覆盖。示例：“记录 12 组，肌群可归类 10/12，负重容量覆盖 7/12；其中 3 组自重另列”。分母不能混用，未知时就显示未知。

7 天窗口另记已核实训练日和缺口。没有明细不等于没练，没有某肌群记录不等于本周零组；只有覆盖已验证后才计算完整周差额。

### 1RM 仅作辅助估计

优先报告真实同重量次数提升，1RM 不作为容量功能前置。若沿用 Epley，初始只允许审核过的动作、明确口径、较低次数且接近力竭有依据的组；候选为 2–10 次、逐组 RIR 0–2。这是工程限制，不是普适生理阈值。首期公式只用实际完成次数，保留 RIR 和估算偏低的可能；趋势比较要求同一努力资格，不把 RIR 从 2 降到 0 造成的差异当力量提升。若以后使用“次数＋RIR”，须另建模型版本与不确定性，不能悄悄切换。成功单次是实际完成重量，不自动等于真正最大重量；高次数、未知努力、自重总负荷未知或器械不可比时不出 1RM。估算变化不能自动宣布真实 1RM 个人纪录。

## 四、来源资格按输出分别判断

分别保存测量资格、映射资格和推荐资格，不用一个“已确认”布尔值控制全部结果。

| 输入情形 | 可以输出 | 暂不输出 |
| --- | --- | --- |
| 只有厂商参考名 | 有来源的动作展示；若有区域字段可作厂商部位参考 | 规范身份、精确肌群剂量、动作处方 |
| 明确代码＋审核映射，训练记录无冲突 | 标注厂商来源的估计肌群汇总 | 冒充用户确认、实际肌肉激活、恢复完成 |
| 上项再满足工作组资格、窗口完整、个人约束可用 | 按正式规则给有置信说明的肌群优先建议 | 仅靠目录指定高强度动作或重量 |
| 用户明确确认/纠正 | 采用确认范围，覆盖冲突的设备推测 | 代填未确认的 RIR、疼痛、器械或口径 |
| 未知代码、区域不清或冲突 | 保留组次、明确负重并指出缺口 | 猜肌群、补训练量、把未知训练日当休息 |

这是待实现的新规则，不是添加字段就自动升级记录。每个进入建议的条件均需独立测试；参考汇总与达到资格的汇总分别保存。无需要求用户确认每一组才提供帮助，也不能把厂商图示当生理测量。用户确认优先但不能由系统代填。

## 五、下次肌群推荐采用约束排序

每个肌群记录最近主要/辅助训练时间、近 7 天直接/间接/等效工作组、此前完整周的个人范围、可比动作表现、明确的局部酸痛/疼痛、来源和覆盖。窗口用 `activity_day`，间隔用实际小时，不能跨零点就算多恢复一天。

1. 先应用伤病限制、明确疼痛/异常症状和当天整体训练强度边界。局部痛感优先，不能用准备度高覆盖；未反馈不等于确认无痛，条件式建议不写成健康事实。
2. 排除近期高负荷且仍有不适的部位；恢复信息不足时给保守选项，不用固定 48/72 小时宣告恢复。
3. 剩余肌群优先个人计划本来安排、相对该肌群自身目标/可比历史剂量较少、近期主要训练较少的部位。周差额需要完整记录，不能跨肌群按绝对组数多少排序，让小肌群长期被判欠量。没有个人目标或可比基线时只考虑覆盖、近期暴露、习惯和可用训练日，不拿十组标准强行补量。
4. 识别复合动作重叠：胸推涉及三头和肩部，背部训练涉及肘屈肌。腿部安排考虑近期长跑、间歇或坡跑，但不把跑步公里数折算成深蹲组数。
5. 给一个首选、一个备选及理由。分化标签只作偏好，固定推拉腿顺序由此规则替代；输出说明哪些缺失信息可能改变结论。

合成案例：“昨日胸推，三头也参与；完整记录显示本周背部直接训练较少，今天优先背部，腿部结合明日跑步安排。若肩肘不适，则改为恢复或无痛部位。”存在未知力量训练时，只能说“已记录部分显示”，不能断言背部没练。

健康目标先重视持续参与、主要肌群覆盖和个人适宜剂量。ACSM 每周至少两天力量训练可作一般参考；增肌人群较高组数的结果不变成所有人的最低任务。进阶优先“双进阶”：同动作/器械下连续可比训练达到计划次数、努力程度合适且没有已知不适后，再考虑最小可行加重；不同时增加重量、组数和频率，不每周自动乘 1.05。

现有 7/28 天负荷比直接判断“有效/过度训练”应改为中性的“相对近期增加/相近/减少＋覆盖”。比值只能描述变化，不能证明刺激有效、恢复完成或伤病风险。与[跑步方案](running-performance-model.md)共用 ACWR 和加量审核边界。

## 六、每次评价与改进

先给事实、分项评价和最多两条改进，再判断能否总评。候选框架为目标完成 40%、强度与剂量适配 40%、执行表现 20%。力量执行表现只评价可观测的计划组次、负重/次数稳定性、明确休息或努力反馈，不评价看不到的动作技术。

目标、完整组次、剂量口径和适用执行证据是总分前提；缺必需项时不补零或重分权重，只展示可用分项。RIR 等可选信息缺失不扣分。容差、分段曲线和权重按健康/力量/增肌目标预先定义并回放，不能事后挑一个好看的分数。减量周、维持训练和短时训练也可以符合目标，不因吨位低天然低分。

建议指向具体可检验改进，例如：“同器械同负重，最后两组次数下降且明确反馈接近力竭；下次保持重量，按现有目标调整休息，再观察稳定性。”缺少休息或 RIR 记录时只描述次数变化，不断言休息不足或强度过高。

## 七、实现与验收

1. **目录与资格**：补完整配置和区域解码证据、版本化映射与失败测试，消除宽泛名称回退；分别支持厂商参考和审核映射展示。
2. **容量和肌群日历**：拆开负重与肌群识别资格，保存逐组事实、直接/间接组数、估计范围与覆盖；日报、晚报、周报共享快照。
3. **建议与评价**：用约束排序替代固定轮换，回放目标与局部反馈的影响，撤掉不成立的过度训练/有效刺激判断；评分规则验证后再开放总分。
4. **个性化校准**：足够的明确反馈与可比历史支持后再校准剂量和间隔，不能以“没有抱怨”或“按时训练”充当恢复成功标签。

沿用 adapter → 规范事实 → ProfileLoader → intelligence → 快照 → 报告投影。映射/模型更新记录版本与影响日期，创建有范围的分析任务；renderer 不查库，历史快照不原地改写，映射更新不重复推送。字段设计时再核定 schema，优先沿用结构/加字段，不预设破坏性换库。

验收至少包括：

- 全量代码唯一性、命名空间、原始区域数组、区域版本和已声明映射依据；8 类菜单码与 46 个人体区域 ID 隔离，未知项保持未知。
- 腿弯举/手臂弯举、中英文歧义、器械变式、单侧/双侧、主次交叉、暂定条目及用户冲突，不能仅以“匹配到”判正确。
- kg/lb、单只/双只、零值哨兵、自重/辅助、缺重量/次数、未知热身；肌群未知时明确重量仍可记容量，重量未知时明确肌群仍可记组数。
- 合成卧推 3 × 8 × 40 kg 的账面容量为 960 kg·次，三头按三组间接组另列，不称三头承受 480 kg·次。更换动作后总吨位上升不自动宣布进步。
- 保留不同次数组原序；重复同步、晚到数据不重复计组；训练后才取得的反馈不能进入训练前推荐；同日两场、跨午夜和 `as_of` 正确。
- 不完整明细、未知日、窗口截断不生成完整周零值；展示与建议资格分离；辅助系数变化会翻转推荐时降级。
- 昨日推类且三头酸痛、两天前腿部但今日长跑、全身训练、完整周缺口及历史不完整，分别验证首选/备选与解释；不强制轮换或按天数宣告恢复。
- 先跑目录、普通/流式解析、持久化、ProfileLoader、力量、周报、决策、报告目标测试，再跑 `tools/check.py backend`、`tools/check.py docs`、`git diff --check`。本次文档检查不代表上述功能已实现。

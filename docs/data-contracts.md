# 数据合同

[文档中心](README.md) | [当前架构](architecture.md) | [Zepp](zepp.md) | [报告与渠道](reports.md)

本页说明进入分析和对外报告的事实资格。字段的完整类型和版本以 `src/vitalis/domain/models.py`、`src/vitalis/intelligence/contracts.py` 和运行服务 `/openapi.json` 为准。

## 事实与来源

规范事实至少保留用户、来源、来源范围、设备（如有）、单位和观测时间。健康观测、厂商日指标、训练摘要、训练明细和用户反馈是不同类型，不能因为字段名称相似就合并。分析结果还保留 `analysis_run_id`、schema/intelligence/decision/evidence 版本和生成时间。

数据集的 `source_mode` 与供应商 `source` 独立：真实、合成和离线回放分别为 `real`、`mock`、`replay`。用户数据集首次声明后不能换模式；改用独立用户或数据库。同步请求冻结模式并纳入幂等身份，执行模式不一致时拒绝请求。报告的 `report_context.source_mode` 来自保存的输入标签，不根据当前配置反推；未标记输入显示 `unknown`。`replay` 标签只表示显式离线输入。当前回放系统保留加密不可变原始响应、payload hash、观测/获取时间、schema/parser 版本和分析输入 manifest；回放写入独立用户数据集，不创建来源凭据、同步尝试或投递意图。回放结果先用 `replay diff` 逐表列出与原用户事实的差异，确认后 `replay apply` 才替换原用户该窗口的事实，并保存被替换的行供 `replay undo` 恢复；操作见[运维](operations.md)。

常用单位如下：

| 字段 | 合同单位与语义 |
| --- | --- |
| 睡眠时长、深睡、REM、浅睡、清醒 | 分钟；零和缺失不同。 |
| 步数 | 步；只在来源明确观测时出现。 |
| 活动/训练时长 | 分钟；训练摘要和活动时长不是同一指标。 |
| 距离 | `km`；没有单位或转换依据时不计算容量。 |
| 心率 | `bpm`；HRV 的 `value_ms` 是毫秒。 |
| 训练负荷 | 厂商负荷或明确算法字段；不能当作通用能量单位。 |
| 重量 | 优先 `weight_kg`；原始单位不明时保留未知，不把数值猜成公斤。 |
| 次数、组数 | 次数是每组或记录明确给出的 repetitions；组数只在真实组次有依据时出现。 |

时间戳通常以 UTC 保存，报告按配置时区（默认 `Asia/Shanghai`）解释本地日。日内区间使用明确截止时刻；跨日睡眠按解析后的本地报告日期归属。`period_start`/`period_end` 是包含端点的本地日期范围，`generated_at` 是生成时刻，`as_of` 表示数据看到的时刻。

## 信号与基线

信号注册表 `src/vitalis/intelligence/signals.py` 为每个规范指标登记源字段、单位、日期语义（`sleep_day`、`activity_day`、`calendar_day`）、资格、覆盖规则、可见渠道（晨报、晚报、Hermes、API）、是否进入决策（`yes`、`no`、`shadow`）以及缺失或迟到时的处理；新信号先登记再进入分析。逐信号状态为 `AVAILABLE`、`PARTIAL`、`STALE`、`UNKNOWN`、`INSUFFICIENT`，整份报告的 `data_quality` 不能代替逐信号状态。个人基线取窗口内每日值的中位数和 MAD，窗口长度随比较记录在 `baseline_window_days`。

HRV、血氧、压力和 Charge 等密集样本流在入库事务里同时写日级特征 `daily_signal_features`：每个本地日、每个流（来源、范围、设备、单位）一行，记录落在合格范围内的样本的中位数、最小/最大值、最新值、样本数、覆盖分钟数和首末观测时刻，以及被范围拒绝的样本数。分析对目标日和前一天读原始样本，更早的日子读特征；特征点的样本数、覆盖分钟数和最新值参与计数、日覆盖和“取最新值”的信号，因此基线、覆盖和取值与逐样本读取一致。特征带写入时的时区，时区不同不复用。

Zepp 的 `hrv` 端点只返回手动单次 HRV 测量（SDNN），平时为空；夜间 RMSSD 来自 `wellness/hrv_rmssd`。分钟心率端点（`heart_rate/minute_endpoint`）对上传密集心率文件的手表一直为空，分钟心率来自 `heart_rate/dense_file`。这两个端点为空是正常结果，不做停更告警。

## 缺失、零和不可比

- 缺失字段保持 `null`、空列表或明确不可用状态；绝不补零、拿旧快照填充或把未知训练日改成休息日。
- 零只有在来源明确报告零时才成立。没有步数记录不是零步，没有力量明细不是零组。
- 来源、设备、单位或时间口径不同的记录不直接比较；同一用户历史也必须满足相同截止时刻和资格条件。
- 可选 HRV、密集文件或动作详情缺失只影响相关特征，不阻塞整份报告。必需信号不足时使用 `INSUFFICIENT_DATA`，不提供对应推断或处方。
- `observed_fields`、coverage、`sample_count`、`distinct_days` 和 `limitations` 解释观测覆盖；它们不是伪造的测量值，也不自动代表数据质量概率。
- Open Health 的 42 天训练负荷只使用持久同步账本验证的日期。完整窗口、分页和预算都合格时才设置 `upstream_coverage_verified`；未验证日保持 UNKNOWN。有训练但缺心率明细仍不可评分，摘要截断不会把遗漏训练改写成休息日，训练和心率输入遵守 `as_of`。
- 分析不再截断高频样本：历史日读日级特征，近两天读全部原始样本。

## 分析与报告

Daily、Morning、Weekly、Monthly 和 briefing 投影共享同一分析快照，但展示顺序不同。日历周为周一至周日的完整周，日历月为完整本地月份；滚动窗口必须标记 `period_mode=rolling`。月报的日均、有效日数和频率要使用正确分母，不以不同月长的原始总量直接判断改善。

比较应就地标明窗口、基线、单位、有效日数和来源。`association` 只表示个人统计关联，不表示因果；厂商睡眠分数、readiness、Charge 等按来源标签描述，不替代 Vitalis 的决策状态。0–100 准备度和身体信号预警在日常分析里计算（`intelligence/readiness.py`）。准备度由 HRV（昨晚 lnRMSSD 与 7 日均值各半，对 60 日正常区间 = 中位数 ± 0.5 个稳健标准差；连续 2 天 7 日均值在区间外才改 HRV 状态，30%）、睡眠（昨晚时长对 28 日个人参照、7 日净睡眠负债（多睡可抵少睡）、入睡时间规律，20%）、静息心率（15%）、Zepp 晨起 Hybrid Charge（当天最大值对前 60 天，20%）和近期负荷（急慢性比 0.8–1.3 为中性，加量过快才扣分，15%）的稳健 z 分数合成，每项在个人常态时为 50，缺分项时按剩余分项重分权重并标明。显示分数 = 70 + 0.9 ×（合成分 − 50），像成绩一样读：个人平常水平是 70，< 60 偏低、60–74 正常、75–84 还行、≥ 85 较好（用户 2026-10-14 定）；晨报关键记录第一张卡显示分数、影响最大的 3 个因素（晨起 Charge 单独列出），存在 `recovery.readiness_*`；卡片末尾附晨起 Charge（与醒来时的值在 377 天里 348 天相同）对前 60 天个人中位数，低于 20 分位标“偏低”、高于 80 分位标“偏高”（少于 14 天不比较），存在 `recovery.wake_charge*`。60 天回放里新算法与晨起 Charge 的秩相关 0.68（旧版 0.55），用户确认状态差的 10-01 为 43 分、今天（10-14，用户自评恢复正常）为 70 分。训练安排依据的恢复状态由显示分数的分数段决定（< 60 受抑制、60–84 正常、≥ 85 较好；用户 2026-10-14 确认），按信号计票的结论存在 `recovery.vote_state` 备查，没有分数时仍由计票决定。当天有身体信号预警时加一条 `BODY_SIGNAL_WARNING` 事件，并把高强度或正常训练降为轻量（驱动因素 `BODY_SIGNAL_WARNING`）。用户在 2026-10-14 看过 60 天回放（6 个预警日中 10-01 至 10-04 用户确认确实休息一般，09-17、09-18 记不清）后确认接入。`open_health_insights` 和个人反应模型仍是 `shadow_only` 输出，只在离峰批处理里计算并存进 `shadow_results`，不进日常分析和报告，也不改变 `decision`；离峰批处理也继续记录准备度和预警结果供周度跟踪；Hermes 上下文读取最近一次开放健康影子结果并标出是否过期。身体信号预警看静息心率、HRV、呼吸频率、皮温偏差和血氧的最近两晚，两晚同向偏离 28 晚个人范围才算一个信号，两个以上同时偏离（HRV 下降加一项升高，或两项升高；血氧看下降）才预警，只建议降低强度，不做疾病判断。

训练反应按 T+0 到 T+3 窗口记录每个指标：`not_due`（窗口未到）、`missing`、`partial`、`available` 或 `confounded`（被后续训练或活动混杂），持续恢复另有 `sustained`、`not_sustained` 等状态。个人关联只检验预先登记的假设，在 60 和 90 天窗口上计算，记录日期语义、样本数、覆盖和混杂比例，经 Benjamini–Hochberg 校正后 q ≤ 0.05 才算显著。两者只出现在周报、月报和 API。

力量训练记录保留动作名称、来源、单位、真实组次和每组次数。`12 / 10 / 8` 不得改写为 `3 × 10`；设备识别与用户确认分别标记，没有冲突的有效设备记录可直接展示，但不能声称用户已确认。未知动作不能推断为某个动作，未知重量不能计算容量。

每周负荷目标取最近 4 个完整周的周均设备训练负荷 × 1.05（目标是综合健康，温和递增）；参照窗口里有未核实的日子就不给目标。近 7 天对近 28 天周均的比值大于 1.3 为“过量”、1.05–1.3 为“提升”、其余为“维持”。本周已完成超过目标 110% 时当天安排改为恢复；已完成至少一半目标且超过按天进度 1.5 倍时为“已超前”；落后于按天进度的 75% 时，今天的份额最多比平均分配多 25%；跑步时长由今天的份额除以近 28 天每分钟负荷的中位数得到。力量动作按主要/次要肌群映射（次要肌群按一半计），容量按权重分到肌群。

用户反馈必须由用户明确提供。RPE 需要关联已完成训练；`workout_id` 与 `workout_source` 必须成对出现。反馈、推荐完成、事件确认和训练确认是独立写入，不由 PushPlus 发送、打开、沉默或 Hermes 未回复触发。

## API 与写入

所有用户范围 API 使用 Bearer 令牌；`X-User-Id` 只做一致性检查。GET 报告和查询只读已保存结果，不启动同步或分析。`POST /api/analysis-runs` 与 `POST /api/sync-jobs` 返回任务受理信息，写请求使用 `Idempotency-Key`；需查询 `GET /api/jobs/{job_id}`，直到 worker 保存结果。

资料 patch 使用当前 revision，遇到冲突先重新读取。Skill 的幂等文件记录请求指纹；响应不明确时复用同一个文件，不能创建新键盲重试。原始反馈通过标准输入传递，令牌、健康记录和真实凭据不能进入 URL、日志、样例或快照。

## 校验失败如何处理

无单位、无来源、时间冲突、非法范围、跨用户或已撤销来源的记录应拒绝或保持不可用，并记录可诊断的非敏感原因。解析器不能把厂商未知枚举映射成已知动作；新增映射要补协议证据和回归测试。修改合同时同步更新 `tests/`、生成 API 参考和本页，不通过删除约束来让检查变绿。

## 观测与身份

`User` 是本地所有者；每个 `(user_id, source)` 由一个 `SourceAccount` 负责，账号以 `(source, vendor_id)` 全局唯一。厂商凭据只通过 `SourceAccount` 关联并加密保存，`User` 和凭据表不再各自持久化一份厂商用户 ID。账号撤销只使凭据、配对/设备链接和在途同步失效，不删除本地用户或已经保存的健康事实；重新配对会增加账号 fencing epoch，撤销前创建的 worker 即使在重新授权后也不能提交。

每条观测保留用户、来源 `source`、语义范围 `source_scope`、设备 `device_id`、单位 `unit` 和适用的时间/日期；跨设备、来源或单位的原始数值不直接相加或平均。缺失设备在内部可用非 null 键满足唯一性，在对外接口保持缺失。时间戳按 UTC 存储，每日计算和训练开始日按 `VITALIS_TIMEZONE`（默认为 `Asia/Shanghai`）归档；未结束的本地日不能当作完整一天。设备上传同毫秒多条样本以独立 `sample_id`/`sample_ordinal` 辨别并幂等落库，原始测量毫秒时间不添加伪造微秒；没有设备 ID 时仍按来源身份保证唯一性，对外设备归属保持未知。

### Balance 2 Bridge 身份与结算

`POST /api/connect/zepp/device-link` 签发只显示一次的设备上传令牌；服务端只保存令牌摘要，令牌不能读取用户健康接口，也不能用 `X-User-Id` 替代 Bearer 身份。`POST /api/bridge/batches` 每次写入先在同一数据库事务中条件确认令牌未撤销、所属本地用户仍存在，再更新 `last_seen_at` 并保存合格样本；撤销、删除或并发改变所有权时整批不写入并返回认证失败。应用层只接受协议 v2 的心率事实：`sample_id` 必须包含并匹配毫秒时间与 `sample_ordinal`，时间限于当前时刻前 31 天至后 5 分钟，心率限于 20--240 bpm。永久拒收逐条结算且不重试；合法样本的重复批次按完整身份幂等确认，同一毫秒的不同 ID 不合并、不伪造微秒。设备链接提供的 `device_id` 是已知的 Balance 2 capability；其他入口缺少设备身份时仍保持未知，不从上传内容推断。

活动的未知 `steps`、`active_minutes`、`calories`、`distance_km` 保持缺失，旧数据的默认 `0` 没有观测证据时不是真值。距离仅在已知单位下换算；泛称热量 `role=unspecified` 不等于总能耗，同一日不同入口的重复读数不相加，训练热量不混成日总。无摄入记录不能推断热量赤字。

`GET /api/health/range` 的范围聚合沿用这一语义：没有合格观测的指标返回 `null`，明确观测到的零才参与平均或合计；空白日期仍计入请求的时间块，但不计为 `days_with_data`。

`workouts` 是规范训练事实，身份是 `(source, workout_id)`；按本地日重建的 `training_records` 是派生摘要，不是每页追加的计数器。详情 `WorkoutDetail 5.1` 存储类型化观测与已知来源；训练心率不自动证明来自某一设备。真实动作身份只能来自明确厂商组或用户确认。力量 `lap_62` 的有限组观测留在 `observed_sets`，不能冒充 `explicit_exercises`、肌群覆盖或处方依据；未知动作代码和重量单位保持未知。实际组次数在规范模型、存储及 HTTP 确认中是正整数或 `null`，仅计划处方的重复范围使用展示文本。用户确认可用空列表明确撤回，当前有效确认与每次变更的不可变修订记录分开保存；撤回后恢复为有证据的厂商观测视图。重量原数值与单位分开，单位未知不能生成确定 kg 容量。训练心率、负荷、热量和睡眠阶段缺少来源字段时保持 `null`，明确观测到的零才是零。Zepp 字段及其证据见[Zepp](zepp.md)。

## 原始健康查询

原始健康读取由 `application/health_query.py` 的 `HealthQuery` 统一组装，存储适配器只返回脱离 ORM session 的值对象；聚合逐行读取时由端口上下文限定数据库 session 生命周期，不把 ORM 对象交给应用层。API 路由只负责 Bearer 用户范围、日期交换与默认值、730 天上限、分页/预算参数和 HTTP 状态码；不会在路由中重新实现来源、设备、单位或时间聚合。

`GET /api/health/metrics/{metric}` 的时间窗口是半开区间 `[from, to)`，即恰好位于 `to` 的样本不返回；不带时区的请求时间按 UTC 解释，比较与跨度校验前先统一为 UTC。`raw` 结果保留 `source`、`source_scope`、未知的 `device_id`/`unit` 以及有证据时的 `sample_id` 和 `sample_ordinal`；最多返回最早的 50,000 条，用额外一条探测设置顶层 `truncated`，不表示其余样本已读完。`1h` 与 `1d` 聚合始终按来源、语义范围、设备和单位分组，不能跨身份平均；逐行累加完整窗口的 `count`、均值、最小和最大值，不受 raw 记录数上限截断。`1d` 使用配置时区的本地日，时区偏移和夏令时产生的 23/24/25 小时 UTC 窗口保持原样；聚合输出超过 50,000 组时明确拒绝（413），不会伪造部分结果。流式聚合限制峰值内存，不免除长窗口数据库扫描成本。`dense-files` 的文件列表也多取一条以标记顶层 `truncated`，`payload_decoded` 只描述本次返回的文件；预算耗尽不等于完整覆盖。

`daily_metrics` 按本地日期、来源、范围、设备和单位返回稀疏厂商事实；`dense-files` 只返回索引覆盖和解码状态，不暴露私有文件 ID。`workouts` 与详情按 `(source, workout_id)` 隔离，详情中的类型化样本保持时间顺序。`token-status` 只读取已保存的账号/凭据元数据和浏览器链接状态，不为 GET 解密厂商 secret 或发起网络验证。

## 分析资格

请求目标日的分析是显式写操作；每次运行保留不可变 `AnalysisRun` 和相应快照，健康智能 GET 只读取已生成且仍符合当前资格的结果，缺少快照返回 `404`。资料修改会递增 profile revision；反馈、资料及训练偏好的有效修改还会在同一写事务中递增用户的 `analysis_input_revision`。分析保存所用 revision，并在提交与当前快照读取时核对；旧快照保留用于审计但不会被当成新输入下的结果。新反馈可能使历史日期的报告暂时不可读，需显式重新分析；幂等重放和无变化的偏好 patch 不推进 revision。`report_context` 包含时区、目标日是否完整、最近观测和训练历史的 `COMPLETE` / `PARTIAL` / `UNKNOWN` 状态；未知训练日不是休息日。报告把事实、推断、建议及证据分开，不用旧快照、厂商分数、默认零或模板处方填补关键缺口。安全门控包括伤痛、恢复不足和训练历史未核实；晨间睡眠完整但训练覆盖不足时只提供已知事实，不给训练剂量。

### A15 纯分析输入与确定性

分析由 `vitalis.application.analysis.analyze(dataset, request, policy)`
统一计算。应用层先准备脱离 ORM 和网络的 `AnalysisDataset`，包括规范事实、
来源/单位/时间资格、训练覆盖、反馈、建议关联和活动健康事件的先前状态；
缺失仍保持缺失，不在纯入口补零或推断动作。`AnalysisRequest` 显式携带目标
日期、UTC `as_of`、时区、同一分析 run ID、输入 revision 与配置摘要；`AnalysisPolicy`
显式携带算法/证据版本、证据引用和 `open_health_insights` 的 shadow-only
开关。纯入口不读数据库、网络、进程设置或当前时间，也不生成随机运行/建议
标识。相同 dataset、request、policy 必须得到字节一致的 Daily、固定 7 日
Weekly、固定 28 日 Monthly、晨间、个人响应/关联和 Open Health 结果。

事件生命周期只根据输入的先前活动状态计算候选转换；应用发布事务仍负责
重新校验输入栅栏、持久化事件和观察，并在最终事件与候选事件不同时从相同
准备输入重建 Weekly、Monthly 及返回的晨报，再保存同一 run 的快照并完成任务。
晨晚报是合格快照的非持久展示投影，不在路由、Skill 或模板中重新计算健康事实。
同一周期的最新快照按成功 run 的完成时间及 run ID 选取；上下文只拼接同一 run
的组件，缺项不会从旧 run 填补。配置、目录和规则摘要属于应用层输入；它们变化时旧快照不能被当作当前建议。通知意图
由定时分析在同一发布事务中创建；`GET /api/deliveries` 只返回当前用户的
`pending`、`deferred`、`uncertain` 等状态和清洗后的调度元数据，不返回租约令牌或
供应商/内部错误正文。

### A17 当前结果新鲜度

`analysis_input_revision` 是用户范围的当前分析输入栅栏。每日事实、稀疏日指标、时序样本、密集文件索引/解码状态、设备型号、规范训练及其详情、派生训练日、力量标签刷新、训练建议关联和厂商身份映射的实质变化，都会在同一写事务中递增它；首次绑定来源账号或撤销后恢复也会推进 revision，重复绑定已活跃的同一身份不推进。资料、偏好和反馈沿用同一规则。数据库用条件冲突更新判断实质变化，避免并发写入以旧读覆盖新值。重放、无变化写入以及只更新训练详情 `fetched_at` 的刷新不递增；同步接口仍返回原有的接受/解析/写入计数。

训练覆盖只接受带有 workouts chunk 证据的终态 `SyncAttempt`（成功、部分完成或失败）；例行更新 `SyncStreamState` 不会单独使报告失效。终态覆盖改变即使没有新增训练事实（例如成功的空响应）也会递增 revision；租约失效或事务回滚的写入和 revision 一并回滚。分析发布前会再次锁定并核对输入 revision，配置指纹还会核对时区、智能版本、决策/证据版本、已核验目录版本和随包规则内容。所有当前报告读取都必须同时满足这些条件；旧快照仍可用于审计，但不能作为当前建议。

HRV 的 RMSSD、SDNN、睡眠 HRV 不混为同一量；按设备和范围各自与个人基线比较。仅有心率不能推导逐搏 HRV；设备功能宣传不等于型号准确性验证。开放健康洞察 `open_health_insights` 始终标注 `shadow_only`，不能修改决策。用户确认的 `sex`、HRmax 等资料不能从年龄公式、训练观测或设备分区自动填充。反馈只记录用户明确提供的内容；训练关联必须同时指定 `workout_source` 和 `workout_id`。个人关联始终是描述性的 `association_only=true`，不代表因果。

当前 `/api` 的非成功 HTTP 响应统一返回 `{ "code": string, "message": string, "retryable": boolean, "request_id": string }`，保留真实 HTTP 状态码；同一次请求的 `X-Request-ID` 与正文 `request_id` 一致。`code` 是稳定的机器可读错误类型，`message` 是固定、安全的展示文案，不能从验证输入、Bearer/Zepp 凭据、健康原文、供应商响应或 SQL 异常拼接。`retryable` 只表示服务建议稍后重试，写操作仍需持久幂等键；`401`/`403`、不存在的资源、幂等冲突及无效输入不建议自动重试。客户端排障可记录 `request_id`，不得记录请求正文或凭据。成功响应与逐条设备样本拒收结构不受本错误合同影响。

字段级请求/响应和单一 `APIError` 定义由当前运行服务的 `/openapi.json` 与 `/docs` 提供；本指南只维护跨端点的语义，不复制接口字段表或错误码表。
